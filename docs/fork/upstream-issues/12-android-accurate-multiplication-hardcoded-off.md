# Android: `shaders_accurate_mul` is hardcoded off in the Android config reader, so Android and desktop silently disagree from one tree

**Shape:** new issue. Possibly the cause of open #1445, and of #1292 / #440 which were closed stale.
**Searched first:** `gh issue list -R azahar-emu/azahar --search "accurate multiplication" --state all`, `"shaders_accurate_mul"`, `"accurate multiplication android default"`. Nothing filed for *this mechanism*. Four threads are adjacent and matter:

- **#1445 (OPEN, `bug`)** — "Pokemon X - Certain pokemon have white buggy textures", Adreno, Android 14, 2123.3. Reporter: *"This color glitch does not happen with Citra."* No cause identified in the thread.
- **#1292 (CLOSED, stale)** — "Incorrect Color For Some Water-type Pokemon In Pokemon Y". Same symptom.
- **#440 (CLOSED, stale)** — "all pokemon type water glitch white". Same symptom, oldest.
- **#1136 (CLOSED, `priority - high`)** — "(Android) Accurate multiplication and asynchronous shader compilation cannot be independently disabled in 2122-rc1". Different bug, same setting, and the reporter noted in passing that *"the config file generated by this build also doesn't seem to have values associated with these settings"* — which is the blank-key half of what is described below.

If this is filed and confirmed, #1445 gets a pointer to it and #1292 / #440 are candidates to close as duplicates of #1445 rather than as stale.

---

## Summary

Every setting on Android is read through `Config::ReadSetting`, which falls back to the shared default in `src/common/settings.h`. **One setting is not.** `shaders_accurate_mul` is read directly with a fallback of `false`, hardcoded in the Android reader, while the shared default is `true`.

The result is that desktop Azahar runs with accurate multiplication **on** and Android runs it **off**, out of the same source tree, with nothing in the UI or the config file to indicate a disagreement. The key in a freshly generated `config.ini` is blank, so it looks untouched; the switch in the settings UI shows off; and the emulator quietly contradicts its own default.

## Environment

- Azahar: observed on `master` in a fork checked out at `2026-09-09`. The two lines in question are long-standing and are not fork changes — verify the exact upstream commit before filing (checklist below).
- Device the config came from: AYN Thor, Android 13 (API 33), `ro.soc.model=QCS8550` (SM8550 / Snapdragon 8 Gen 2), Adreno 740, driver 512.676.53.
- The bug is **not device-specific**. It is a source-level divergence and applies to every Android build.

## Reproduction

1. Install any Android build and complete setup so a `config.ini` is generated.
2. Look at the key — it is blank, as generated:

```
adb shell "grep -n 'shaders_accurate_mul' /sdcard/azahar/config/config.ini"
# shaders_accurate_mul =
```

3. Launch any title and read the setting back out of the log:

```
adb logcat -d | grep Renderer_ShadersAccurateMul
```

4. Compare against a desktop build with an equally untouched config, whose log line for the same key reads `true`.

## Expected

A blank key means "no opinion", and the emulator uses the shared default from `src/common/settings.h`, exactly as it does for the other ~40 settings the Android reader handles. That default is `true`, so Android should log `Renderer_ShadersAccurateMul: true`.

## Actual

Android logs `false`. Desktop logs `true`. Same tree, same blank key, opposite behaviour.

## Root cause

`src/android/app/src/main/jni/config.cpp:142-143`, in `Config::ReadValues()`:

```cpp
    Settings::values.shaders_accurate_mul =
        android_config->GetBoolean("Renderer", "shaders_accurate_mul", false);
```

Every neighbouring line goes through the template instead:

```cpp
    ReadSetting("Renderer", Settings::values.graphics_api);
    ReadSetting("Renderer", Settings::values.async_shader_compilation);
    ReadSetting("Renderer", Settings::values.use_hw_shader);
    ...
```

and `ReadSetting` for a `bool` (`config.cpp:91-94`) passes the shared default:

```cpp
template <>
void Config::ReadSetting(const std::string& group, Settings::Setting<bool>& setting) {
    setting = android_config->GetBoolean(group, setting.GetLabel(), setting.GetDefault());
}
```

The shared default is `true`:

```cpp
// src/common/settings.h:563
SwitchableSetting<bool> shaders_accurate_mul{true, Keys::shaders_accurate_mul};
```

So the hardcoded `false` is the only thing producing the divergence. The Kotlin enum agrees with the hardcoded value rather than the shared one (`BooleanSetting.kt:83`, `SHADERS_ACCURATE_MUL(..., false)`), so the settings UI shows the switch off and looks self-consistent — which is why this is invisible from the outside.

Two things make it hard to notice from the user side:

- **A blank key reads as untouched.** `jni/default_ini.h` generates every key with an empty value, so a user inspecting `config.ini` sees `shaders_accurate_mul =` and reasonably concludes nothing is overriding anything.
- **Nothing warns.** There is no log line saying the Android reader is departing from the shared default, because from the reader's point of view it is not departing from anything.

I have not found a commit message or comment explaining the intent. If it is deliberate — a mobile performance decision — then it should at minimum be `settings.h`'s `#ifdef ANDROID` default, next to the ones already written that way (`async_shader_compilation` at `settings.h:551-558` and `use_vsync` at `settings.h:564-568` both do exactly this), rather than a silent override in the reader that the Kotlin layer then has to duplicate.

## Why it matters: the per-title table does not cover the games that report it

`src/common/hacks/hack_list.cpp` force-enables accurate multiplication for a fixed list of titles under `HackType::ACCURATE_MULTIPLICATION` / `HackAllowMode::FORCE`, applied on Android at boot via `jni/native.cpp` → `GPU::ApplyPerProgramSettings`:

- The Legend of Zelda: Ocarina of Time 3D (JPN/USA/EUR/KOR/CHI)
- Mario & Luigi: Superstar Saga + Bowser's Minions (USA/EUR/JPN)
- Mario & Luigi: Bowser's Inside Story + Bowser Jr.'s Journey (USA/EUR/JPN)
- Mario & Luigi: Paper Jam (JPN/USA/EUR/EUR demo)

**Pokémon X and Y are not in that list**, and there is no Pokémon title anywhere in `hack_list.cpp`. So on Android those titles run with accurate multiplication off unless the user finds the switch, which is precisely what #1445, #1292 and #440 describe: wrong, over-bright colours on specific surfaces, on Adreno, on Android.

The most telling line in #1445 is the reporter's own: *"This color glitch does not happen with Citra."* That is what a default divergence looks like from the outside — the same game, the same phone, a different answer.

**This is a hypothesis, not a confirmed diagnosis.** I have not reproduced #1445 or verified that enabling the setting fixes Froakie's colours. See the checklist.

## The fix, in prose

Delete the special case so the setting reads like every other one:

```cpp
    ReadSetting("Renderer", Settings::values.shaders_accurate_mul);
```

and change `BooleanSetting.kt:83`'s declared default from `false` to `true` so the UI stops disagreeing with the engine.

If the `false` is intentional for mobile, the equivalent-but-honest form is an `#ifdef ANDROID` default in `settings.h` alongside the two that already exist there, so that one file remains the single source of truth for what a blank key means and the Kotlin default can be derived from it rather than guessed.

Either way the substantive question for a maintainer is which default Android should have. The bug being reported here is narrower and not a matter of taste: **the answer should not be written in two places that disagree, in a way no user can see.**

No patch attached — it is a two-line change and the choice of which of the two shapes to take is a maintainer's call.
