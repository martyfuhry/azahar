# melonDS on the AYN Thor: resume/sleep crashes — cursory research

## 1. Which melonDS

It is **rafaelvcaetano/melonDS-android** (package `me.magnum.melonds`). There is no official Android port: `melonDS-emu/melonDS` has no Android sources, no gradle/JNI/Kotlin files, no `android` branch, and the org only owns `melonDS` and `melonDS-switch` ([repo](https://github.com/melonDS-emu/melonDS), [contents](https://github.com/melonDS-emu/melonDS/tree/master)). Latest upstream release is desktop 1.1 (Nov 2025); rafaelvcaetano ships 2.0.1 (May 2026) plus nightlies. Press coverage calling it "melonDS on Android" means his port ([Android Authority](https://www.androidauthority.com/melonds-nintendo-ds-update-1-10-3534310/)).

Rendering: **OpenGL ES only — no Vulkan anywhere in the tree** (0 files match "vulkan"). Core renderer is Software or OpenGL (`video_renderer` pref). Presentation is EGL/GLES3 on a `SurfaceView` from a dedicated `FrameRenderThread` (`ui/emulator/render/FrameRenderCoordinator.kt`, `GlContext.kt`), with two strategies: `SurfaceBackRenderer` (eglCreateWindowSurface + swapBuffers) and, on Android 13+, `SurfaceFrontRenderer` (HardwareBuffer + EGLImage + `SurfaceControl.Transaction`, front-buffer rendering). Lifecycle: `EmulatorActivity` declares `configChanges=orientation|screenSize|screenLayout|…` and `launchMode="singleTask"`, so rotation does not recreate it; `onPause` → `viewModel.pauseEmulator(false)` + stop Choreographer, `onStart/onStop` → `frameRenderCoordinator.addSurface/removeSurface`.

## 3. Does the same class of bug exist? (4 ideas)

1. **No foreground service, no autosave on pause.** `app/src/main/AndroidManifest.xml` has only WorkManager's `SystemForegroundService` (dataSync) — nothing keeps emulation out of the cached tier. `EmulatorActivity.onPause` pauses the core and never writes a state; `saveState` is only reachable from the pause menu/quick slot (`EmulatorViewModel.kt:497+`). ~~This is the whole of #1624-after-the-fix.~~ On Marty's device the losses are not cached-tier reclaims at all, so this framing does not hold for him; the finding itself (no FGS, no autosave on pause) is still an accurate reading of the code. **Already being fixed by someone else**: [PR #1666 "Restore sessions after Android process death"](https://github.com/rafaelvcaetano/melonDS-android/pull/1666) (corigne, 2026-09-06, +2401/−224, reproduced on a Thor with real LMKD pressure). Don't duplicate it.
2. **Front-buffer path is fragile across suspend** (`render/SurfaceFrontRenderer.kt`): a child `SurfaceControl` is built from `surfaceView.surfaceControl` and only rebuilt when `hardwareBuffer == null` or the size changes — never when the *Surface identity* changes. If the Surface is recreated at the same size, transactions go to a dead layer: black picture, audio fine (#1665 symptom). Effort: S–M.
3. **`managedSurfaces` / `surfacesPendingRemoval` race** (`render/FrameRenderCoordinator.kt`, `addSurface`/`removeSurface`/`destroySurfaces`): `onStop` posts `MSG_DESTROY_SURFACES`; a fast screen off/on re-adds the same `EmulatorSurfaceView` before that message runs, so `destroySurfaces()` tears down the freshly re-created EGL surface / SurfaceControl. `addSurface` never removes the view from the pending list. Effort: S.
4. **GL work off the render thread**: `addSurface` runs on the UI thread and calls `EmulatorSurfaceView.setSurfaceRenderer` → old renderer's `stop(glContext)` → `glDelete*` with no current context (silent no-ops → leaked HardwareBuffers/FBOs). Also no `EGL_CONTEXT_LOST` detection anywhere: one `GlContext` is created in `FrameRenderCoordinator.init` and shared with the core's GL context, never revalidated after wake. Effort: S each, M to do properly.

## 4. Upstream policy

Neither repo has an AI policy: melonDS-android has **no CONTRIBUTING, no CODE_OF_CONDUCT, no PR template** (only `.github/ISSUE_TEMPLATE/melonds-issue.md`, FUNDING, workflows). Upstream melonDS's [CONTRIBUTING.md](https://github.com/melonDS-emu/melonDS/blob/master/CONTRIBUTING.md) is a pure code-style guide with no mention of AI/LLM/generated code. I found no maintainer statement on AI PRs in either tracker; I could not check their Discord. **So: an AI-assisted PR is not prohibited, and disclosing it in the PR body is the right move** — nothing forbids it, and nothing promises it will be welcomed. Style compliance matters more upstream (strict PascalCase/brace rules).

PR style, melonDS-android: rafaelvcaetano is responsive on issues (5-day turnaround on #1624) but has a **slow, review-heavy PR backlog** — 11 PRs open, some since 2022; #1524 sat ~5 months before a detailed "your thinking is adequate, the implementation can be finer" review; translation PRs from 2024 merged in 2026. Expect substantive review and long latency. Discussing in an issue first is the documented preference (the issue template pushes non-bugs to Discussions).

## 5. Practical workarounds for Marty now

- ~~**Update to the nightly** (the #1624 dual-screen fix is only in nightlies, not in 2.0.1).~~ **Withdrawn 2026-09-09.** #1624 is ruled out for his crashes and no upstream version is known to fix them. The nightly is not harmful, but recommending it implies a fix that is not established. The useful action instead is **to reproduce a crash and have the record read within three days**, before Android's ~3-day DropBox retention drops it.
- **Turn off the external/dual-screen output** while sleeping the device — the only actual crash fixed so far was on that path, and #1641 asks for a toggle. Prefer **OpenGL over Software** for #1665 (reporter says Software is worse). Keep internal resolution low, and **disable Rewind** (`enable_rewind`, Settings → General) — it holds a rolling buffer of states and is pure LMK bait.
- **Manual quick-save before closing the lid** is the only reliable protection today; melonDS writes no autosave. (It protects against losing a session however it is lost, so it survives the correction above — but note it is a mitigation for the *symptom*, and the crashes themselves are unexplained.) Sideloading corigne's PR #1666 branch (and Komalis' [PR #1664](https://github.com/rafaelvcaetano/melonDS-android/pull/1664) for RTC-on-lid-open) gets both features early; both authors tested on a Thor.
- **Alternative emulators**: DraStic (free since the Tropic Haze/Nintendo action, no longer on Play) is the usual community fallback for stability, and the RetroArch melonDS DS core exists; I found **no Thor-specific community consensus** I could verify — Reddit is not fetchable by my tooling, so treat "what Thor owners actually use" as **unverified**.

# Addendum: the alternatives compared (Thor / Odin 2)

| | FG service / survives background | Autosave + restore | Surface loss on wake | Thor 2nd screen | Thor/Odin sleep reports |
|---|---|---|---|---|---|
| melonDS-android | **No** (only WorkManager dataSync FGS) | **No** (manual slots only) | GLES; own EGL/SurfaceControl path, no context-loss check | **Yes** (`ExternalPresentation`) | #1624, #1659, #1665 |
| RetroArch | **No** service; NativeActivity, `singleInstance` | `savestate_auto_save`/`auto_load` = on *content close*, not on background | Mature `APP_CMD_TERM/INIT_WINDOW` teardown+rebuild (GL and Vulkan) | **No** (open FR) | #19240, #8786 |
| DraStic (free) | No (closed source, unmaintained since 2023) | Auto-resume of last state is a long-standing feature; unverifiable | Unknown | No | forum reports, no Thor data |
| NooDS | **No** service | Flushes SRAM (`writeSave`) on pause, no state | `GLSurfaceView` — EGL context destroyed/rebuilt by the framework; safest pattern | No | none found |
| Lemuroid | **Yes** — `GameService` foreground service (`FOREGROUND_SERVICE_DATA_SYNC`) | **Yes** — `autosave` pref, saves state on leaving, restores next launch | libretro GLRetroView (GLSurfaceView) | No | none found |

**RetroArch, the interesting one.** Its Android manifest has **no foreground service** ([manifest](https://github.com/libretro/RetroArch/blob/master/pkg/android/phoenix/AndroidManifest.xml)) — so it is exactly as killable as melonDS while asleep. Its autosave options (Settings → Saving → Auto Save State / Auto Load State) fire on *content close* and on clean quit, **not** when Android backgrounds or kills the process, and they had a multi-month regression where the auto slot was never written at all ([#16080](https://github.com/libretro/RetroArch/issues/16080), reported on an Odin 2 Pro, fixed by [#16084](https://github.com/libretro/RetroArch/pull/16084)). SaveRAM Autosave Interval does protect in-game saves. So **RetroArch's options do not avoid this class of problem**: they avoid losing progress on a *deliberate* exit, not on an OS kill. Its surface handling is the genuinely better half — the Android platform driver tears down and rebuilds the GL/Vulkan context on `APP_CMD_TERM_WINDOW`/`INIT_WINDOW`, which is why RA rarely wedges the way melonDS #1665 does; but [#8786](https://github.com/libretro/RetroArch/issues/8786) ("magnetic case… resumes on black screen… input & sound still working", open since 2019) is the same lid-close symptom, and [#19240](https://github.com/libretro/RetroArch/issues/19240) is an open AYN Thor crash report on the latest nightly, gl and vulkan alike. RetroArch also has **no external-display support on Android** ([#17985](https://github.com/libretro/RetroArch/issues/17985)), so no Thor bottom screen.

**Lemuroid** ([repo](https://github.com/Swordfish90/Lemuroid)) is the only one architecturally immune-by-design: a real foreground service holds the process at perceptible importance while a game runs, and autosave-on-leave + restore-on-launch means an OS kill costs you at most the last few seconds. It runs DS through the libretro melonDS core (it ships a `MelonDS` touch layout). Downsides: no second screen, no dual-screen layout editor, older core, fewer options. I found no Thor/Odin sleep reports against it — but it is also far less used on those handhelds, so absence of reports is weak evidence.

**DraStic** is closed source and effectively unmaintained since the free release, so none of this is auditable; the only sleep-related report I found is unresponsive controls after resume on ArkOS handhelds ([ArkOS known issues](https://github.com/christianhaitian/arkos/wiki/Known-issues)), not Android. **NooDS** ([repo](https://github.com/Hydr8gon/NooDS)) uses a plain `GLSurfaceView`, so the framework destroys and rebuilds the EGL context across pause for it — the black-screen class basically cannot happen — but it has no foreground service, no state autosave (only a 3 s SRAM flush loop), and no second screen.

**Recommendation.** Nothing on Android is free of this: only Lemuroid combines a foreground service with autosave/restore, and it gives up the Thor's second screen. Marty should stay on **melonDS-android nightly** — it is the only one with real dual-screen support and the most active maintainer — with **OpenGL renderer** (not Software, per #1665), **Rewind off**, low internal resolution, battery **Unrestricted**, and a **manual quick-save before closing the lid**, and should sideload [PR #1666](https://github.com/rafaelvcaetano/melonDS-android/pull/1666) + [PR #1664](https://github.com/rafaelvcaetano/melonDS-android/pull/1664) if he wants autosave-on-death and RTC sync today. Keep **Lemuroid** installed as the "leave it asleep for days" option for single-screen play, and treat **RetroArch** as a fallback only — its autosave protects clean exits, not OS kills, and it cannot drive the bottom screen at all.
