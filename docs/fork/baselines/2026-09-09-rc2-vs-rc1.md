# thor-v1-rc2 candidate vs thor-v1-rc1 — 2026-09-09

- RC1: `azahar-thor-rc1-59f9592f4-vc40000000.apk`, versionName `thor-v1-rc1-1-thor`,
  versionCode 40000000. Tag `thor-v1-rc1` (`f218c0cdb`) plus a cherry-pick of `a2e6ff781`
  (the thor flavor), giving `59f9592f4`. The tag itself predates the flavor, so rc1 could
  not otherwise be installed as `org.azahar_emu.azahar.thor`.
- RC2 candidate: `azahar-thor-rc2-acf5f0133-vc40000000.apk`, versionName
  `thor-v1-rc1-36-thor`, versionCode 40000000, from `thor/main` tip **`acf5f0133`**.
  (`thor/main` has moved on since, but only by documentation commits — `acf5f0133` is
  code-identical to the tip at the time of writing.)

Both APKs are `assembleThorRelease -Pandroid.injected.testOnly=false
-PversionCodeOverride=40000000`, so `adb install -r -d -t` replaces in either direction and
no uninstall was ever needed. Each install was followed by a `dumpsys package` versionName
check that had to match the APK's before the pass was allowed to start, and every boot
timeline carries its own git banner (`59f9592 | HEAD-thor-v1-rc1-1-g59f9592f4` vs
`acf5f01 | HEAD-thor-v1-rc1-36-gacf5f0133`) as a second, independent identity proof.

The delta between the two builds is all of wave 2: `fix/thor-display`,
`perf/secondary-window`, `perf/trim-memory`, `perf/boot`, `feat/thor-defaults` and
`fix/resume-input-focus`.

## Conditions

Galaxy Z Fold5 `R3CW705DSTF`, SM-F946U1, Android 16 (API 36), package
`org.azahar_emu.azahar.thor`, ROM `/storage/emulated/0/roms/3ds/acnl.3ds`, launched with
the VIEW intent at `…/org.citra.citra_emu.activities.EmulationActivity`. Phone **folded**
(`cmd device_state print-state` = 0), the 2316x904 cover panel active, `mWakefulness=Awake`
and `deviceLocked=0` throughout; no `KEYCODE_SLEEP`/`POWER`/`WAKEUP` was sent, so state C
(screen off) is out of scope, and the app was never uninstalled. Battery on charge.
`/sdcard/azahar/config/config.ini` has `autosave_mode = 2`, `resolution_factor = 3`,
`perf_log_interval` non-zero.

**scrcpy was running for the whole session** (host `scrcpy --serial R3CW705DSTF`, and its
`"scrcpy"` 904x2312 VirtualDisplay is visible in every `dumpsys SurfaceFlinger --display-id`
capture below). It was left alone because it is the user's. That makes these absolute
numbers **not comparable with the 2026-09-08 rc1-vs-baseline table**, which was explicitly
taken scrcpy-free; the rc1-vs-rc2 deltas here are still valid because both builds were
measured back to back in the same state, 8 minutes apart, on the same device with nothing
else changed. Note that `measure.sh identity` reports "scrcpy: not running" on this phone —
it greps `ps -A` for `scrcpy`, but the device side of scrcpy runs as `app_process`. The
reliable check is a virtual display named `scrcpy` in `dumpsys SurfaceFlinger --display-id`.

`device.lock` was held for the whole measurement (08:20:51–08:38:26 EDT); the two builds and
the 4x pass ran inside one `flock`. `mCurrentFocus` was sampled at the start of each pass and
before the foreground samples; no foreign app fronted display 0 during either pass, and no
screen-derived (screencap) measurement is used in this document at all. One run per metric,
no repeats — treat differences under ~5 % as noise unless a mechanism is named.

Raw captures (boot logs, meminfo, thread snapshots, timestats, SurfaceFlinger and display

`~/Development/azahar-builds/measure-rc2-2026-09-09/` — `out-rc1/`, `out-rc2/`,

## Reading the numbers

**The boot-with-resume win is real and mechanically explained.** rc1's `RunCitra()` loads the
disk shader/pipeline cache at t=0.673 s, then the autosave load at t=1.411 s runs
`System::serialize → Shutdown/Init`, which throws that renderer away: 738 ms of work spent on
an object that no longer exists. rc2 does the resume first (`Begin load of slot` at t=0.626 s)
and loads the cache at t=1.854 s into the renderer that will actually run the game. The 738 ms
of removed waste matches the −722 ms of measured boot delta almost exactly. Both builds do end
up with a populated 9587 KB pipeline cache — in rc1 that happens as a side effect of
`PipelineCache::SwitchCache` inside the load, not because of the pre-load pass — so L-1's real
payoff is the deleted duplicate pass, not "the cache would otherwise be empty".

**Frame pacing is materially better, by way of a 60 Hz panel.** rc1 presents a 60 fps guest to
a 120 Hz panel, so the present2present histogram is the familiar two-mode 8 ms / 25 ms split
(814 and 796 samples) with p95 = p99 = 25 ms. rc2 puts the panel in its 60 Hz mode
(`6bcf7a807`) and 1784 of 1796 intervals land in the single 16 ms bucket: p95 and p99 both
drop from 25 ms to 16 ms. Neither build drops or janks a frame, so this is smoothness, not
throughput — and it is a deliberate refresh-rate change, worth stating plainly rather than
reading as a generic "9 ms faster".

**The memory win is the second swapchain, not the surface cache.** EGL mtrack falls 49 MiB in
the foreground and 41 MiB behind HOME, and thread count drops by 3; GL mtrack, native heap and
VmRSS are all unchanged within noise. That is exactly the shape of `perf/secondary-window`
removing a 1080p `HiddenDisplay` swapchain and its present path, confirmed directly by the
display dumps. TOTAL PSS follows it down by 50 MB foreground / 43 MB paused (−3.6 % / −3.1 %).

**Paused CPU is already at target on both builds** (0.33 % and 0.36 %, against the kit's
< 0.5 % goal), so the wave-1 audio fix is holding and there was nothing left for wave 2 to win
here. Foreground CPU is 1.2 pp higher on rc2 — within single-run noise, and pointing the wrong
way only in a window where rc2 also renders 3 % more frames.

## Anomalies and caveats

- **M-2's memory trim never fired.** rc2's `CitraApplication.onTrimMemory` logs
  `Trimming memory at level N` and the core logs `Releasing cached resources on request of the
  frontend`; neither string appears anywhere in 5.5 minutes of logcat covering HOME + 3 minutes
  parked, and GL mtrack behind HOME is within 1.5 MB of its foreground value on **both** builds.
  The process sits at `Proc # 2: prcp M/S/FGS`, `procState=FGS`, `oom_score_adj=200`,
  `isFrozen=false` because of the foreground service, so Android never sent it a
  `TRIM_MEMORY_UI_HIDDEN`-or-worse callback while it was parked. The 41 MB of EGL that *does*
  disappear at HOME is the framework releasing the swapchain, and it happens on rc1 too. M-2 is
  therefore **unverified on this device**, not disproved: the code path was never entered. The
  next pass should either drive it directly (`am send-trim-memory <pid> HIDDEN`) or measure it
  on a build without the foreground service.
- **The "discard the first boot after an install" rule did not reproduce this time.** rc1's
  first boot after install was *faster* than the same scenario later (3193 ms vs 3527 ms), and
  rc2's were 2804 ms and 2805 ms. Both first boots were still discarded, as required, but the
  page-cache effect the 2026-09-08 pass saw (4608 ms → 3535 ms) was not visible here.
- **Not comparable with the 2026-09-08 table.** scrcpy was on for this pass and off for that
  one, `resolution_factor` is 3 here (that pass did not record it), and rc1's GL mtrack today
  (450 MB) sits between that pass's baseline (770 MB) and candidate (312 MB) figures. Use this
  document only for rc1-vs-rc2.
- **`measure.sh identity` cannot see scrcpy.** It greps `ps -A` for `scrcpy`, which never
  matches because the device side runs as `app_process`; it printed "scrcpy: not running" for
  both passes while scrcpy was demonstrably running. The `virtual disp:` line it prints from
  `SurfaceFlinger --display-id` is the check that actually works. Worth fixing in the kit.
- **Per-thread CPU rows still understate the process total** in the foreground window (≈48 %
  of rows against a 48.9 % / 50.1 % process total here, so much closer than last pass, but the
  join still drops threads created or destroyed inside the window). The paused windows, where
  the thread set is stable, are the ones safe to read thread by thread.
- **Both builds keep a foreground service after HOME** (`fg-service`, `oom_score_adj=200`,
  `isFrozen=false`), so neither was frozen or cached during the paused window.
- The autosave decision alternates with `.lastboot`, so each pass deliberately captured both
  scenarios: the measured cold boot ignored the autosave, and a later boot (after a HOME that
  wrote a fresh autosave) resumed it.
- A `MediaProvider` warning — `Database update failed while renaming
  …/states/0004000000086300.autosave.cst.tmp` — precedes the `Autosave written` line on **both**
  builds. The autosave file is correct on disk afterwards (18 MB, current timestamp) and it
  loads, so this is cosmetic, but it is a pre-existing rename-over-SAF wart, not new to rc2.
